# Defect reports

**Empty on purpose.** These must be defects *you* actually found and reproduced. One real, well-written defect report is worth more in an interview than twenty invented ones — because you will be asked to talk through one, in detail, and only a real one survives that.

## Rules

1. Reproduce it at least twice before writing it up. If it does not reproduce, say so in the report — an intermittent defect is still a defect, and noting the intermittency is a mark of a careful tester.
2. One defect per report. Two problems in one report cannot be tracked or closed independently.
3. Attach a screenshot for anything visual.
4. Severity is about impact on the system; priority is about urgency of the fix. They are not the same, and being clear on that distinction is an ISTQB-level thing interviewers probe.

## Naming

`BUG-001-short-description.md`, numbered in the order found.

## Severity guide

| Severity | Meaning in this project |
|---|---|
| Critical | Data loss, wrong money figure posted, system unusable |
| High | Core flow broken, wrong stock quantity, no workaround |
| Medium | Function incorrect but a workaround exists |
| Low | Cosmetic, wording, minor usability |
